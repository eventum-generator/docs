A **project** in Studio corresponds to a generator directory on disk — a [generator.yml](/docs/core/config/generator-yml) file and its supporting resources (templates, scripts, samples, pattern files). The Projects section lets you browse, create, and edit generator configurations without writing YAML by hand.

## Project list

The Projects page shows all generator directories discovered under the configured `generators_dir` path. The heading counts them and states how many are in use by at least one instance.

<ThemedImage
  lightSrc="/images/studio_ui/projects_light.png"
  darkSrc="/images/studio_ui/projects_dark.png"
  alt="Projects page in Eventum Studio"
  className="rounded-lg border mt-2"
/>

The table has the following columns:

| Column | Description |
|--------|-------------|
| **Project name** | The name of the generator directory. Click it to open the project. |
| **Instances** | One badge per instance running this project, each carrying that instance's status color. A project with no instances shows "Not used". |
| **Modified** | When any file in the project directory last changed. |
| **Size** | Total size of the project directory. |

**Project name**, **Modified** and **Size** are sortable — click a header to switch direction.

### Filtering

- **Search by name** — text filter on project names.
- **Search by instance** — text filter on the names of the instances using a project.
- **All / In use / Unused** — restricts the list to projects that have instances, or to those that have none.

### Creating and managing projects

**Create new** scaffolds a new generator project: pick a name, and Studio writes a minimal `generator.yml` you can build on.

Each row carries a menu with **Edit**, which opens the project, and **Rename** and **Delete**. Renaming a project also updates the instances that point at it, so a rename never leaves an instance without a config.

## Project workspace

Clicking a project name opens the workspace: a full-screen layout of four docked panels around one generator.

<ThemedImage
  lightSrc="/images/studio_ui/project_input_light.png"
  darkSrc="/images/studio_ui/project_input_dark.png"
  alt="The project workspace with the Input stage selected"
  className="rounded-lg border mt-2"
/>

| Panel | What it holds |
|-------|---------------|
| **Explorer** (left) | The project's file tree. |
| **Editor** (center) | Open files as tabs. |
| **Inspector** (right) | The plugins of the selected stage and their parameters. |
| **Console** (bottom) | The tool that belongs to the selected stage. |

The vertical dividers and the console's top edge are draggable, so you can give whichever panel you are working in more room. The console also collapses to its header, or expands to fill the window, using the two controls on its right.

### The stage switcher

The bar at the top carries the three stages of the [generator pipeline](/docs/core/concepts/generator#the-three-stage-pipeline) — **Input**, **Event** and **Output** — each showing which plugins it currently holds. Selecting a stage retargets both the Inspector and the Console; the Explorer and the Editor stay as they are, so you keep the file you are editing while moving between stages.

Every tool keeps its state while you are away. Generated timestamps, a running debugger session and typed-in sample events all survive switching stages and come back as you left them.

### Saving

**Save** in the top right writes the configuration and every modified file at once. While anything is unsaved, a badge next to it names what is pending — `config`, `2 files`, or `config + 2 files`. Modified files are also marked with a dot on their editor tab, and **Save file** above the editor saves just the file in front of you (also `Ctrl/Cmd+S`).

Leaving the workspace with unsaved changes raises a confirmation first, whichever way you navigate away.

## Explorer

The Explorer lists every file and directory inside the generator directory, each with a type-appropriate icon and its size. Clicking a file opens it in the editor.

The panel header holds **New file**, **New folder** and **Upload files**. The right-click menu of the tree offers the same two creation actions, plus **Rename** and **Delete** on a file or directory. Files are moved by dragging them onto another directory, and dropping files from outside the browser uploads them into the directory they land on.

The `generator.yml` file is what makes the directory a project, so it cannot be renamed, moved or deleted from here.

---

## Editor

Files open as tabs and stay open until closed, so several templates can be kept side by side. A middle click closes a tab; closing one with unsaved changes asks first.

- **Syntax highlighting** for Jinja, Python, YAML, JSON, Markdown, CSV and the other formats a generator holds.
- **Autocomplete** for Jinja templates and Python scripts, covering the context variables and helper modules available in a template.
- **Find and replace** (`Ctrl/Cmd+F`) — a match counter, **Match case**, **Regular expression** and **Whole word** toggles, next and previous match, select all matches, and a replace row that replaces the current match or every match at once.
- **Go to line** (`Ctrl/Cmd+Alt+G`).

<ThemedImage
  lightSrc="/images/studio_ui/project_editor_search_light.png"

Files above 10 MB are not opened in the editor — the tab reports the size and the limit instead. Sample data that large is better edited outside Studio.

## Input stage

The Inspector lists the configured input plugins and the parameters of the selected one. **+** adds a plugin, and the delete icon beside a plugin removes it. Below the form, **Configuration** shows the YAML the form produces, which is the quickest way to check what will be written to disk.

The console holds the **Timestamps preview**: it runs the input stage without starting a generator, so you can confirm the schedule produces the traffic shape you intended.

| Control | Description |
|---------|-------------|
| **Plugins** | Preview one input plugin, or leave it empty to merge all of them as a running generator would. |
| **Count** | How many timestamps to generate for the preview. |
| **Time span** | Bin width of the histogram, for example `30s`, `5m`, `1h`. |
| **Timezone** | The zone the timestamps are shown in. |
| **Skip past** | Excludes timestamps that have already passed. |

**Generate** runs the preview and fills two views: **Distribution**, a histogram of timestamps over time with the total count, and **Timestamps**, the generated values themselves. Daily peaks, uniform spacing and bursts are all visible in the histogram at a glance — the screenshot above previews three overlaid [time patterns](/docs/plugins/input/time-patterns) and shows their combined daily rhythm.

## Event stage

The Inspector holds the single event plugin and its parameters. For the [template plugin](/docs/plugins/event/template) that includes the picking mode, the template list with their chances, the samples, and the parameters passed to every render.

The console offers two views of the same live plugin instance: **Debugger** and **State**.

### Debugger

The debugger produces events on demand, so you can iterate on a template without starting a generator.

<ThemedImage
  lightSrc="/images/studio_ui/project_event_debugger_light.png"
  darkSrc="/images/studio_ui/project_event_debugger_dark.png"
  alt="The event debugger in the project workspace"
  className="rounded-lg border mt-2"
/>

**Start** builds the plugin from the current configuration; the indicator next to it reports the session as running, and **Stop** discards it. With a session running:

| Field | Description |
|-------|-------------|
| **Event timestamp** | The timestamp handed to the plugin. **Auto** keeps it at the current time. |
| **Tags** | Tags to pass alongside the timestamp, as an input plugin would. |
| **Count** | How many events to produce per run. |

**Produce** renders the events and shows them under **Events**, one card each, with a syntax selector for coloring and a copy button per event. Anything the plugin raises appears under **Errors** beside them, with the reason — a template that fails is reported here rather than silently producing nothing.

Editing a template and producing again picks up the change, which makes the loop between editor and output a few seconds long.

### State

The State view exposes the state of the plugin the debugger built, which is what a template reads and writes through `locals`, `shared` and `globals`.

<ThemedImage
  lightSrc="/images/studio_ui/project_event_state_light.png"
  darkSrc="/images/studio_ui/project_event_state_dark.png"
  alt="Template state in the project workspace"
  className="rounded-lg border mt-2"
/>

| Scope | Description |
|-------|-------------|
| **Local state** | State of one template. Select the template to inspect it. |
| **Shared state** | State shared by every template in this generator. |
| **Global state** | State shared by every generator in the application. |

Each table lists keys with their values, typed as object, array or scalar, and large values expand rather than being cut short. Rows can be edited and deleted individually, and each table offers **Sync** to re-read the values, **Add** to insert a key as JSON, and **Clear** to empty the scope.

The State view needs the live plugin the debugger builds, so it becomes available once a session is running.

<Callout type="warn">
Global state is application-wide. Editing it from here affects every running instance, not only the generator you have open. [Scenarios](/docs/studio/scenarios) show which generators read and write which global keys.
</Callout>

## Output stage

The Inspector lists the output plugins in delivery order with the parameters of the selected one, so a generator writing to several destinations is configured in one place.

<ThemedImage
  lightSrc="/images/studio_ui/project_output_light.png"
  darkSrc="/images/studio_ui/project_output_dark.png"
  alt="The Output stage of the project workspace with the formatter preview"
  className="rounded-lg border mt-2"
/>

The console holds the **Formatter preview**, which runs sample events through a formatter and shows the payload that would be delivered:

- **Formatter** — the [format](/docs/plugins/formatters) and its parameters, such as the JSON indent.
- **Events** — sample events as text, one editable card each; **+** adds another.
- **Result** — the formatted output after **Format**, with rejected events listed under **Errors** together with the reason.

Checking a payload here costs nothing and answers the question a full run would answer slowly — whether the events a template emits are actually valid for the format the destination expects.

## When the configuration cannot be loaded

An invalid `generator.yml` leaves nothing for the stages to describe, so the workspace falls back to the Explorer and the Editor, with a notice naming the problem and **Show details** for the validation error itself.

<ThemedImage
  lightSrc="/images/studio_ui/project_config_error_light.png"
  darkSrc="/images/studio_ui/project_config_error_dark.png"
  alt="The project workspace with an invalid generator configuration"
  className="rounded-lg border mt-2"
/>

Fix the file in the editor, save it, then **Reload** to bring the rest of the workspace back. Keeping the editor reachable is the point: a config that a hand edit or a merge left malformed is repaired in the same place it broke.
