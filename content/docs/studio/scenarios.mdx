---
title: Scenarios
description: Group generator instances into named scenarios for coordinated lifecycle control, a live view of the global state they exchange, and a diagram of the data flowing between them.
---

A **scenario** is a named grouping of generator instances that work together as a logical unit. [Projects](/docs/studio/projects) define what a generator does; a scenario defines which instances collaborate at runtime.

For example, a corporate network simulation might have an authentication service tracking user sessions, a web proxy generating HTTP traffic for those users, a DNS resolver publishing the domains it refuses, and a firewall logging connections from the same population. These generators exchange data through [global state](/docs/plugins/event/template/state) and need coordinated lifecycle control. A scenario ties them together.

## Configuration

Scenarios are defined through the `scenarios` field in [startup.yml](/docs/core/config/startup-yml). Each generator can belong to one or more scenarios — just use the same name:

```yaml title="startup.yml"
- id: corp-auth-service
  path: corp-auth-service/generator.yml
  scenarios:
    - corporate-network
    - security-monitoring

- id: corp-web-proxy
  path: corp-web-proxy/generator.yml
  scenarios:
    - corporate-network

- id: corp-dns-resolver
  path: corp-dns-resolver/generator.yml
  scenarios:
    - corporate-network

- id: corp-edge-firewall
  path: corp-edge-firewall/generator.yml
  scenarios:
    - corporate-network
    - security-monitoring
```

Here `corporate-network` groups all four generators, and `security-monitoring` groups only the authentication service and the firewall. There is no separate scenario config file — a scenario exists as soon as any generator references the name.

Scenarios can also be created and managed from Studio, and membership can be changed from an [instance](/docs/studio/instances#overview). Either way the change is written back to `startup.yml`.

The table lists every scenario with its instance count and the states those instances are in, so a scenario that is only half running is visible without opening it. Selecting rows enables **Start**, **Stop** and **Delete** for the whole selection. Each row carries the same lifecycle actions for itself, plus **Edit** to open the scenario, **Rename** and **Delete**.

**Create new** creates a scenario: pick a name and select the instances that belong to it. Deleting a scenario removes the grouping, never the instances.

The header carries the scenario's aggregate status, how many of its instances are running, and **Start all** / **Stop all**, each disabled when there is nothing for it to act on. Where the [Instances](/docs/studio/instances) page treats instances one at a time, this is where a whole simulation is brought up or taken down in one action.

### Data flow

The diagram shows how the instances of the scenario interact through global state: which of them writes which key, and which reads it. It appears once any generator in the scenario uses `globals.set()` or `globals.get()` in its templates.

Hovering an instance or a key highlights the edges that touch it and dims the rest, which is how a key written by one generator and read by three others becomes legible. Clicking an instance in the diagram expands its card below. The diagram can be zoomed, panned and fitted.

### Instances

Each instance in the scenario is a card carrying its status, with a menu for **Start** / **Stop**, **Show metrics**, **Show logs**, **Edit instance**, **Go to project** and **Remove**. Removing takes the instance out of the grouping and leaves the instance itself alone.

A card that uses global state expands to list its templates and, per template, the keys it writes and the keys it reads. Hovering an entry highlights the matching edge in the diagram above, which answers "where does this key come from" in one gesture.

**Add** attaches an existing instance to the scenario.

### Template preview

A template name in an expanded card opens its source read-only, under its own entry, so you can see how `globals.set()` and `globals.get()` are actually used without leaving the page.

## Global state

The panel on the right is a live key-value view of the `globals` dictionary, with a count of the keys and a search over both keys and values. Values are typed as object, array or scalar and expand rather than being cut short.

Individual keys can be added, edited as JSON and deleted, **Sync** re-reads them, and **Clear** empties the dictionary.

<Callout type="warn">
Global state is application-wide — editing it affects every running instance, not only the ones in this scenario. Check the data flow diagram to understand what depends on a key before changing it.
</Callout>
